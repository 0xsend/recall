# Parser Metadata Extraction Spec

## Problem

Claude Code's JSONL format has drifted from what the parser expects. Fields moved from top-level to nested inside `message`, and naming conventions shifted (camelCase at root, snake_case nested). The parser silently returns `None`/`0` for `git_branch`, `git_repo`, `model`, `input_tokens`, and `output_tokens` — no error, just missing data.

This will happen again. The format is not versioned and has changed at least twice. The parser needs a resilient extraction pattern that handles multiple schema variants per field without turning into spaghetti.

## Solution

Introduce a **cascading field extraction** pattern: each metadata field declares an ordered list of paths to try (newest format first, oldest last). A shared `_first_of` utility accepts flat keys or nested key tuples and returns the first non-None match. This is declarative, scannable, and extending for the next format change means prepending one path.

Extract duplicated helpers (`_extract_content_blocks`, `_build_tool_call`, `_extract_bash_command`, `_parse_timestamp`) into `parsers/common.py` so every source parser shares one implementation.

## Domain Model

### Entry metadata (per JSONL line)

Each JSONL entry may contain session-level metadata. The parser accumulates these across all entries to build the `Session` object. The extraction table defines where each field lives across known format versions:

| Field | Current format (2025+) | Legacy format | Oldest format |
|-------|----------------------|---------------|---------------|
| `timestamp` | `entry.timestamp` | `entry.created_at` | — |
| `model` | `entry.message.model` | `entry.model` | `entry.model_name` |
| `cwd` | `entry.cwd` | `entry.working_directory` | — |
| `git_branch` | `entry.gitBranch` | `entry.git.branch` | `entry.git_branch` |
| `git_repo` | `entry.cwd` (derive) | `entry.git_root` | `entry.repo` |
| `source_session_id` | `entry.sessionId` | — | — |
| `input_tokens` | `entry.message.usage.input_tokens` | `entry.inputTokens` | — |
| `output_tokens` | `entry.message.usage.output_tokens` | `entry.outputTokens` | — |
| `cache_creation_tokens` | `entry.message.usage.cache_creation_input_tokens` | — | — |
| `cache_read_tokens` | `entry.message.usage.cache_read_input_tokens` | — | — |

### Shared helpers (parsers/common.py)

Functions used by 2+ parsers that currently exist as duplicates:

- `_first_of(entry, *paths) -> str | None` — try each path (string = flat key, tuple = nested keys), return first non-empty string match (empty strings are treated as absent)
- `_first_int(entry, *paths) -> int | None` — same but coerce to int
- `extract_content_blocks(content) -> tuple[list[str], list[str], list[ToolCall]]` — text, thinking, tool_calls
- `build_tool_call(tool_name, tool_input) -> ToolCall` — construct ToolCall with bash parsing
- `extract_bash_command(tool_name, tool_input) -> str | None` — extract bash command from tool input
- `parse_timestamp(value) -> datetime | None` — ISO timestamp parsing
- `js_object.parse_js_object_literal(text, pos, *, consts) -> tuple[dict, int]` — read one JavaScript object literal (Codex `exec` arguments)
- `js_object.collect_string_consts(source) -> dict[str, str]` — map `const NAME = "literal"` declarations for shorthand resolution
- `js_object.StaticBindings(source).exec_commands() -> Iterator[str]` — every command an exec call's `cmd` template evaluates to when its interpolations resolve statically (REQ-PARSE-017); source must be at most `STATIC_PROGRAM_CHARS_MAX` characters
- `skills.derive_skill_names(tool_name, tool_input, bash_command, *, cwd) -> tuple[str, ...]` — every skill a tool call loaded, each once
- `skills.derive_skill_name(tool_name, tool_input, bash_command, *, cwd) -> str | None` — the first of those, for the single stored `skill_name`

## Requirements

- `REQ-PARSE-001`: The Claude Code parser must extract `model` from `entry.message.model`, falling back to `entry.model` and `entry.model_name`.
- `REQ-PARSE-002`: The Claude Code parser must extract `git_branch` from `entry.gitBranch`, falling back to `entry.git.branch` and `entry.git_branch`.
- `REQ-PARSE-003`: The Claude Code parser must extract `input_tokens` from `entry.message.usage.input_tokens`, falling back to `entry.inputTokens`. Same pattern for `output_tokens`.
- `REQ-PARSE-004`: The Claude Code parser must extract `source_session_id` from `entry.sessionId`.
- `REQ-PARSE-005`: Shared content-extraction helpers (`extract_content_blocks`, `build_tool_call`, `extract_bash_command`, `parse_timestamp`) must be consolidated into `parsers/common.py`. Every source parser (Claude Code, Codex, Pi Agent, Grok, Kimi Code) must import from `common` instead of defining private duplicates.
- `REQ-PARSE-006`: The `_first_of` utility must accept a mix of string keys (flat lookup) and tuple keys (nested lookup), trying each in order and returning the first non-None match of the expected type.
- `REQ-PARSE-007`: The `_first_int` utility must follow the same cascading pattern as `_first_of` but coerce values to `int`, returning `None` on type/value errors.
- `REQ-PARSE-008`: The `cache_creation_input_tokens` and `cache_read_input_tokens` fields from `entry.message.usage` should be accumulated alongside `input_tokens` and `output_tokens` when present.
- `REQ-PARSE-009`: Existing test fixtures using the legacy format must continue to pass. New fixtures must cover the current (2025+) format to prevent regression.
- `REQ-PARSE-010`: The Codex and Pi Agent parsers must be updated to import shared helpers from `parsers/common.py` but their field extraction logic is unchanged (no cascading needed — their formats are stable).
- `REQ-PARSE-011`: The Codex parser must extract `input_tokens` and `output_tokens` from the absolute maximum cumulative `payload.info.total_token_usage.input_tokens` and `payload.info.total_token_usage.output_tokens` across `event_msg` entries whose `payload.type == "token_count"`. Codex `total_token_usage` is monotonic, so the maximum over a full parse or any incremental suffix represents the latest cumulative session total in that parsed range. Incremental correctness is provided by the indexer's source-aware last-wins merge (`REQ-INDEX-014`). `cached_input_tokens` and `reasoning_output_tokens` are subsets and must not be added on top. Sessions with no `token_count` events keep `None`.
- `REQ-PARSE-012`: The Grok parser MUST leave `input_tokens` and `output_tokens` as `None` when parsing `chat_history.jsonl` alone — that file records no token usage. This is correct parser behavior, not a gap; a code comment must document the intent. Exact Grok tokens are filled only by the usage harvester against `~/.grok/logs/unified.jsonl` (root SPEC REQ-USAGE-010+), never invented from transcript length or `signals.json.contextTokensUsed`.
- `REQ-PARSE-013`: The Kimi Code parser must map `wire.jsonl` events as: `context.append_message` → user Message; `content.part` (`think`/`text`) loop events → assistant thinking/content, one Message per LLM step (flushed at step boundaries); `tool.call` → ToolCall on the step's Message; `tool.result` → system Message prefixed with `[tool_call_id: ...]`; `usage.record` → additive token deltas (`inputOther` + `inputCacheRead` + `inputCacheCreation` for input, `output` for output). Deltas are additive, so `kimi_code` must NOT be added to `ABSOLUTE_TOKEN_SOURCES`. `turn.prompt`/`turn.steer` must be skipped — they duplicate `context.append_message`. Wire files under `agents/agent-N/` must set `agent_id` on their Messages/ToolCalls; the session cwd comes from the sibling `state.json` `workDir`.
- `REQ-PARSE-014`: The Grok parser MUST enrich session metadata from sibling sidecar files in the session directory when present and valid: `summary.json` → `started_at` (`created_at`), `ended_at` (`last_active_at`), `cwd` (`info.cwd`), `git_repo` (`git_root_dir`), `git_branch` (`head_branch`), `model` (`current_model_id`); `signals.json` → `duration_seconds` (`sessionDurationSeconds`) only. Sidecar failures are non-fatal. Must NOT map `contextTokensUsed` to token columns. Cross-ref root SPEC REQ-GROK-TS-001–004.
- `REQ-PARSE-015`: Every parser MUST implement `sidecar_paths(path)`, returning the sibling files whose content it folds into session metadata — empty for sources that read only the session file. The returned set MUST stay in lockstep with what the parser actually reads; Grok returns `summary.json` and `signals.json` per `REQ-PARSE-014`. A parser that enriches from a file it does not declare goes stale silently, because the indexer fingerprints only declared sidecars (root SPEC `REQ-INDEX-018`). Returned paths need not exist; missing entries contribute nothing to the fingerprint.
- `REQ-PARSE-016`: The Codex parser must recover the tool calls carried by the `custom_tool_call` payload named `exec`. Codex builds ≥ 2026-07-09 stopped emitting one `function_call` per tool and instead ship a JavaScript program whose `input` invokes `tools.<name>({...})`, sometimes several per program via `Promise.all`. Each inner call becomes its own `ToolCall` named for the inner tool (`exec_command`, `write_stdin`, `apply_patch`, MCP names), in source order, so rows stay continuous with the pre-2026-07-09 shape. Arguments are JavaScript object literals, not JSON — unquoted keys, single quotes, trailing commas, and shorthand properties bound to earlier `const` declarations — and must be read by `parsers/js_object.py`. Values that need a JS runtime (interpolated templates, loop variables, expressions) must be dropped **at any depth** rather than guessed at — a sentinel left nested in `tool_input` fails `json.dumps` at insert time and aborts the whole session's index — and any wrapper with a dropped value, a non-object argument, or no recognizable call must keep its program source under a `source` key. Calls are recognized **syntactically**, and only in executable code: a `tools.<name>(` inside a string literal, a comment, or a regex literal (patch bodies and search patterns routinely carry one) must not be recorded, or the wrapper invents calls that never ran. The same rule governs `const` collection — a commented-out or quoted declaration never bound anything, and taking it as the binding persists a command that never ran. Control flow is deliberately not evaluated, so the count is the program's call *sites*, not its executions — a call in an untaken branch is counted once too often, and a call in a loop is counted once regardless of iterations. Exact accounting would need a JS engine: the rollout's `custom_tool_call_output` carries one combined output blob for the whole program, not per-call results, so nothing in the transcript can reconcile it. Over the local August corpus (5,106 wrappers / 6,299 call sites) no wrapper contained a literal dead branch, while 11% contained a loop — the under-count is the common case, not the over-count. A row with neither `bash_command` nor `tool_input` is the defect this closes: it left 183,725 codex rows text-free and invisible to search, `stats bash`, and embeddings.
- `REQ-PARSE-017`: Skill attribution must cover each harness's real invocation shape. Claude Code and Kimi Code typed `Skill` calls keep the non-empty `skill` argument. Every other load derives names from read-shaped access to a `SKILL.md`. A path attributes when it sits under an installed root directly beneath a home directory — `~/.agents/skills/`, `~/.claude/{plugins,skills}/`, `~/.codex/{plugins,skills}/`, `~/.grok/bundled/skills/`, `~/.pi/agent/{git,plugins,skills}/` — or when it is a checkout laid out like one: the agent-profile source `.../agent-profile/plugins/<plugin>/skills/<skill>/SKILL.md`, or a `.agents/skills/`, `.claude/skills/` or `.codex/skills/` layout such as a repository's own project skills or the dotfiles tree a harness root links to. A checkout read counts wherever it sits, including inside the session cwd, because harnesses load project skills by reading them there; a relative path resolves against the session cwd and stays unattributed without one. Attribution requires a read-shaped act: a read tool (`read`, `Read`, `read_file`, `view`) or whole-file read verb (`sed`, `cat`, `head`, `tail`, `nl`, `bat`, `less`, `more`). Shell segmentation must respect quoting; discovery (`find`, `rg`, `ls`, `wc`), editing (`git diff`, `sed -i`, `--in-place`), quoted pseudo-calls and plain `skills/<name>/SKILL.md` paths remain unattributed. A Codex code-mode `exec_command` program counts a string literal only when the literal is itself a read-shaped command; a bare path literal stays unattributed, and at most 256 literals are examined. A template literal counts only when it is the `cmd` value of the object literal passed directly to `tools.exec_command(...)`, with no later `cmd` key or spread in that object to override it, in executable code (not a comment, `console.log`, file write, `write_stdin`, or an object that is logged or serialized) and resolves statically to such a command: every interpolation is `${name}` or `${JSON.stringify(name)}`, and `name` has exactly one binding occurrence in the whole program — any declaration, parameter (including method shorthand, class methods and defaulted parameters), destructuring target, `for (name of|in ...)` head, assignment, or increment counts as one, judged by the preceding token however much whitespace separates them; assigning to a subscript such as `out[name] = ...` binds nothing. That binding is either a `const` initialized by a string literal and nothing more (`const p = "…".replace(…)` is not), or the variable of `for (const x of arr)` (never `let`/`var`) or `arr.map|forEach|flatMap(x => …)` / `((x, i) => …)` whose template lies inside that loop's body or callback. `arr` is an inline array literal or a `const` initialized by an array literal and nothing more, whose every other use is iterating it with a callback of at most two parameters (element and index, never the array itself), or reading one element or `.length` without reaching further into it (`[`, `.`, a call) or assigning to it; a mutating method, `delete`, index or `length` assignment, nested element change, alias, argument, or spread leaves it unknown. When its items are arrays, the only accepted uses are the destructuring loop itself (`for (const [a, b] of arr)`, `arr.map(([a, b]) => ...)`) and reading `.length`: any element read, single-name loop variable or callback parameter could reach a row and change it. Its at most 64 items are strings or integers, or arrays destructured as `[a, b]`; a template expands to at most 64 commands. Resolution runs only for programs that name `SKILL.md` and are at most 16,384 characters (real programs stay under 7 KB), in a single linear scan, and at most 256 templates are examined. Anything else — `${paths[i]}`, `${r.output}`, string concatenation, an escaped `\${`, `paths.slice(1)`, a template bound to a `const cmd` — leaves the template unattributed. A loop that exits early still counts every element, consistent with REQ-PARSE-016's call-site counting. Code run through `eval`, `Function`, or similar is invisible to this analysis and may change a value it treats as known; programs are agent-written transcripts, not adversarial input. Each skill counts once per program however many of its commands load it. One call may load several skills: every read-shaped segment and path operand counts, shell brace groups expand (at most 64 paths, beyond which the token stays unattributed), and each skill is reported once per call. A name that still holds a shell variable or glob (`$f`, `*`, `?`, `[`) was never expanded and stays unattributed. Names use `plugin:skill` whenever the path identifies a plugin — plugin caches, multi-plugin layouts, `~/.agents/skills/<plugin>/<skill>/`, Pi Agent git clones, and agent-profile source layouts — and otherwise remain bare. The stored `skill_name` column holds the first name.
- `REQ-PARSE-018`: A tool payload that is a bare string must keep its text. `ToolCall.tool_input` is dict-typed, so `build_tool_call` must wrap a string payload as `{"input": <string>}` rather than discarding it — codex sends `apply_patch` as a `custom_tool_call` whose `input` is the raw patch, and dropping it left the row recording only that a call happened. A string already recovered as a `bash_command` is not stored a second time. Inside an `exec` wrapper the same tool is invoked as `tools.apply_patch(patch)`; when the argument is a bare identifier bound to a plain string const the reader already collected, it resolves to the same `{"input": ...}` shape so wrapper and direct forms aggregate. An identifier that is any other expression — a call, a member access, a concatenation — is not recoverable and the row keeps the whole program source instead.
- `REQ-PARSE-019`: A `web_search_call` must keep its whole `action`. A search action carries `query` and no `url`, so reading only `url` recorded nothing for every actual search while opened pages survived.
- `REQ-PARSE-020`: A parser captures a finite source prefix at parse start and acknowledges only newline-terminated records it decoded. `ParseResult.next_byte_offset` is the last committed boundary; `ParseResult.diagnostics` reports unterminated tails, malformed records, and unsupported semantic records without guessing their meaning. The capture digest names the exact bytes consumed and must be verified before the indexer commits derived rows or a checkpoint.

- `REQ-PARSE-021`: Codex `token_usage_record.payload.thread_token_usage` contributes cumulative input/output maxima alongside legacy token-count events; per-response usage is not added again. Tool-search calls retain arguments and their paired results. Compaction snapshots normalize `agent_message` and readable reasoning with the same occurrence accounting as ordinary messages. Native completed `AgentMessage` blocks of type `Text` retain their text; unknown readable native block types produce diagnostics instead of empty messages. Native completed hook prompts, plans and review output retain readable content; review entry retains its supplied target/hint as system metadata. Completed tool activity is correlated by invocation id: canonical response calls/results take precedence in either ordering, while unmirrored calls/results retain source order. An `exec-*` activity within the same observed turn as an `exec` program is a view of that program's decoded calls, not an additional invocation. An exact `{"type":"other"}` compaction placeholder has no recoverable content; unknown fields still produce diagnostics. Unknown or structurally unsupported records remain diagnostic and never authorize replacing existing history.

- `REQ-PARSE-030`: The Kimi Code parser MUST handle the agent wire records. `agent.turn.started` (`turnId`, `queueItemId`) carries no conversation content and is acknowledged without a diagnostic. `agent.turn.ended` declares the turn boundary whatever its `outcome` (`done`, `failed`): the outcome becomes a stop marker on the last message with `ends_turn=True`, anchored via `message_idx_base` in suffix parses. `agent.message.appended` carries one append to the agent's message store: `message.message` is `{role, content parts, toolCalls, toolCallId}` and `message.meta.source` is `input` / `llm` / `tool` / `notify`. ## Invariants

- Cascading field extraction is **newest format first, oldest last**. When the format changes again, prepend one path — do not reorder existing paths.
- `_first_of` and `_first_int` are pure functions with no side effects.
- No schema version detection. A single JSONL file may span format versions (e.g., if Claude Code was upgraded mid-session). Each entry is extracted independently.
- Token accumulation uses `_accumulate_metric` — `None + None = None`, `None + N = N`, `M + N = M + N`.

## Non-goals

- Abstracting field chains into classes/registries. Functions with ordered args are sufficient.
- Changing the `SessionParser` protocol. It already captures the right contract.
- Adding format version headers to JSONL files. We don't control the format.
- Changing Pi Agent field chains. Its format hasn't drifted; REQ-PARSE-029 reads usage counters the parser previously ignored.
- Inventing token usage for providers whose session files do not record it (Grok harvest is a separate subsystem; see root SPEC Fleet Token / Usage Ledger).

## Acceptance Criteria

`REQ-PARSE-021`: Current Codex rollouts preserve developer instructions as system
messages, readable reasoning as assistant thinking, and agent messages with their
recorded author. Turn metadata supplies model/cwd. An item-completed mirror and
response item are matched one-to-one by source id or observed turn correlation;
equal ordinary messages remain separate. Compaction replacement history retains
new readable summary content without replaying already represented occurrences.
Encrypted reasoning/compaction envelopes supply no invented readable content.
Unknown semantic records produce diagnostics and prevent a clean checkpoint in
every adapter. The Codex normalization contract is full-parse only until a
resumable checkpoint preserves its cross-record correlation state.
